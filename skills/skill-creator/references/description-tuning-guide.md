# Description の書き方ガイド

## 原則

Claude がスキルを「呼ぶべきか」を判断するのは、**name + description** の 100 語以内の情報だけです。

つまり：
- **description はスキルのトリガーを決定する最重要要素**
- 短すぎる → スキルが呼ばれない
- 不正確 → 場所違いで呼ばれる
- 複雑さが伝わらない → 「自分でできる」と判断される

## 良い Description の特徴

### 1. 複雑性を明示する

❌ **悪い例** - シンプル過ぎる
```yaml
description: "テスト結果を表示する"
```

✅ **良い例** - 複雑性・多段階処理を明示
```yaml
description: "複数のテストフレームワーク（NUnit/xUnit）の結果を統合解析し、
失敗原因を推測、カバレッジ低下箇所を指摘、パフォーマンス劣化を検出するスキル。
XML/JSON 形式の結果ファイルを自動解析して Markdown レポート生成。"
```

### 2. 具体的な用途を列挙する

❌ **悪い例** - 一般的過ぎる
```yaml
description: "ファイルを処理する"
```

✅ **良い例** - 使用場面を明記
```yaml
description: "JSON ファイルの複数バージョンの差分抽出、スキーマバリデーション、
ツリー構造の可視化、そして大規模ファイル（>100MB）の段階的処理に対応。"
```

### 3. トリガー例を複数含める

```yaml
description: "テスト結果分析スキル。以下のような場面で活用：
- テスト実行後の自動分析・レポート化
- CI パイプラインでの失敗診断
- 開発者からの 'テストが失敗した原因は？' という質問への詳細回答
- カバレッジ低下箇所の自動特定
- パフォーマンス劣化の根本原因推定"
```

### 4. フレームワーク・形式を明記

```yaml
description: "NUnit・xUnit テストフレームワークの XML 出力を解析。
Cobertura カバレッジレポートからカバレッジ率を抽出。
複数の時系列データを比較して劣化傾向を検出。
出力は Markdown・JSON・CSV 複数形式に対応。"
```

## アンチパターン

### 1. 一文に詰め込みすぎ

読みにくく、トリガー判定に失敗しやすい。

### 2. 技術用語をない混ぜ

```yaml
# NG
description: "AsyncIO パイプライン最適化エンジン"

# OK
description: "非同期処理パイプラインの最適化。複数のタスクを並列実行し、
ボトルネック分析と自動チューニングを提供。"
```

### 3. 「〜するスキル」だけ

```yaml
# NG
description: "テストを実行するスキル"

# OK
description: "複数環境でのテスト実行・結果集約・失敗原因分析スキル。
ローカル・CI・ステージング環境での実行結果を統一フォーマットで比較。"
```

## チューニングのコツ

### A/B テストで最適化

```json
{
  "candidates": [
    {
      "id": 1,
      "description": "テスト結果を分析する"
    },
    {
      "id": 2,
      "description": "C# プロジェクトの複数フレームワークテスト結果を統合解析。
失敗原因推定、カバレッジ低下箇所指摘、パフォーマンス劣化検出に活用。"
    },
    {
      "id": 3,
      "description": "NUnit/xUnit テストの自動分析と最適化提案スキル。
カバレッジレポート解析、失敗パターン検出、改善提案を含むレポート生成。"
    }
  ],
  "eval_set": "trigger-eval.json",
  "expected_max_triggers": 20
}
```

各候補で trigger-eval.json を実行し、**test スコア** が最高のものを選択。

## JsonEditor プロジェクト特有の注意点

### テストフレームワーク

- **主**: xUnit（tests/JsonEditor.App.Tests）
- **補**: NUnit 互換モード

### テスト結果ファイル形式

- **XML**: `tests/JsonEditor.App.Tests/TestResults/*.xml`
- **JSON**: Cobertura カバレッジ結果（opencover 形式）

### 典型的なトリガーシーン

```
"テストカバレッジが69%で、前回より下がっている。どこが低いのか分析して"
→ スキルを呼ぶべき場面

"今日のテストは全て成功した"
→ スキルは不要（確認だけ）

"MainViewModel のテストカバレッジが特に低い理由と改善案を教えて"
→ スキルを呼ぶべき場面
```
